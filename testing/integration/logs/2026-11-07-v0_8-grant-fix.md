# v0.8 idle grant-expiry client correction,7 November2026

The user reported STATUS OK, remote IDLE, Motion STOPPED, DRIVE OFF,
sequence0/session707a89e9, followed by START STALE_GRANT with the same
sequence/session/states. The command was rejected before Motion ARM.
This is an actual failed movement attempt, not a physical v0.8 pass.

## Cause and reproduction

STATUS returns the current grant; it does not reset that grant's1000ms
lifetime. Therefore a successful STATUS can report a token with very little
lifetime left. The original Python client treated its subsequent explicit
STALE_GRANT rejection as fatal. Its fake transport tests never expired an
idle grant between STATUS and START. The user's exact transport delay was
not measured; the real controller reproduces the same result at the boundary.

Added a characterization test to the actual `drive_control.c` host fixture:

```text
STATUS t=999 grant=100
START t=1001 -> STALE_GRANT, grant=101, no ARM, sequence unchanged
Same START sequence/values with grant101 at t=1002 -> ARM accepted
```

The controller remains unchanged. The test runs under strict GCC warnings
and ASAN/UBSAN; see `2026-11-07-v0_8-grant-controller-trace.log`.

## Correction and limits

Changed only production `tools/mqtt/drive_cli.py`. For a matching explicit
STALE_GRANT rejection of idle START/TARGET/CLEAR, use the returned new grant
once with the same sequence/values and original deadline. Require unchanged
session, last mutation sequence, target, remote/Motion state/reason/duties,
ready status, output OFF and a different nonzero grant. A mismatch aborts.

This cannot rearm after a lost reply or movement failure: timeouts continue
to retransmit identical bytes; running KEEPALIVE errors, session/state changes,
faults or a second grant rejection abort. The existing run cleanup still
requests STOP and confirms fresh output-off status. No device expiry guard,
lease, wire format, power/wiring or motor output code was changed.

New regression tests failed against the original client with the same
STALE_GRANT message, then passed after the correction. Tests cover the
successful boundary recovery, unchanged request/sequence, one-recovery limit,
lost ACK after recovery, STOP cleanup, rejection/state/session guards,
configuration requests and no recovery for running KEEPALIVE.
